1. Overview

Vayu is an independent, Python-inspired programming language. Its repository contains a C++ frontend, lexer, parser, AST, semantic/type checker, tree-walking interpreter, bytecode compiler and virtual machine, package tooling and editor tools. Source files use .vyu.

Available execution
Tree-walking interpreter (--run) and bytecode VM (--vm)
Native compiler
VIB integration scaffold; native code generation is not implemented
Package tool
Vayu-source tools/nva.vyu and reference registry server
Editor tools
vls, vfmt, vlint and editor extensions
A feature present in the language, examples or roadmap does not automatically mean the current native mode supports it. Execution-mode support must be verified separately.

3. Current execution status

Available: interpreter

vayuc file.vyu --run uses the tree-walking interpreter.

Available: bytecode VM

vayuc file.vyu --vm compiles to Vayu bytecode and runs it in the VM.

Native mode: not implemented

--native and --native-out reach the VIB scaffold and return an explicit not-implemented diagnostic.

Also unavailable

VIR dumping and runtime C emission are not available yet. External-link options are reserved.

7. VIB and the Integrator architecture

VIB means Vayu Integration Backend. It is the integrated compiler/runtime system inside the Vayu repository. Integrator is the architecture it implements. Neither is a separate language or required standalone executable.

VIB is intended to own frontend integration, VIR definition and verification, native lowering/code generation, runtime contracts, artifact emission, optional linker integration, caching, incremental builds, dispatch, diagnostics and conformance evidence.

The current VIB/ directory contains an API scaffold and documentation. VIR, verification, native code generation, artifact caching, incremental compilation and adaptive dispatch remain planned work.

The repository separates frontend, interpreter, bytecode compiler/VM, VIB scaffold, Vayu-source package tool (tools/nva.vyu) and editor utilities. Package commands and registry workflows are under active development; consult the current source documentation for exact scope.

5. Frontend and language semantics

The frontend is the language authority. It turns .vyu source into tokens, syntax structures, and semantic information consumed by the available execution routes. VIB is designed to integrate with this frontend rather than introduce a second parser or a second definition of Vayu.

Lexing and parsing

Recognise source tokens and grammar, build the AST, and report syntax errors with useful source context.

Semantic analysis

Resolve names and scopes, check types and supported constructs, and preserve information needed by later stages.

Diagnostics

Report errors at the source level where possible. A future backend diagnostic should map its failure back to a source location and selected execution mode.

One language contract

Interpreter, VM, and future native execution must agree on observable behavior instead of silently creating separate dialects.

The documented syntax surface includes functions, variables and types, conditions, loops, recursion, strings and collections, slicing, structs/classes, inheritance, lambdas and closures, exceptions, generics, pointers, modules and interoperability foundations. This list describes the language/codebase surface, not a guarantee that every construct is supported by every execution mode.

6. Interpreter and bytecode VM

These are the current execution routes. They should be used for real execution today while native compilation is unfinished.

Tree-walking interpreter

Executes the parsed program directly. It is useful for rapid execution and as a semantic reference for tests.

vayuc file.vyu --run

Bytecode VM

Compiles supported program constructs to Vayu bytecode, then runs the bytecode in the virtual machine.

vayuc file.vyu --vm

Neither route should be described as native machine-code execution. Where interpreter and VM behavior differs, treat the mismatch as a correctness issue to reproduce and test, not as an undocumented language feature.

8. Vayu IR (VIR) and verification

VIR is the in-memory internal representation used by the VIB Integrator path. The current subset has lowering, structural verification, control-flow and opcode checks, and VIR-interpreter execution. It is not the source language or a stable external ABI.

Intended core representation

  • Modules, functions, parameters, return types, typed values and constants.
  • Basic blocks with explicit terminators, branches, calls and returns.
  • Arithmetic, comparisons, conversions, local storage and supported memory operations.
  • Runtime operations, side-effect information and source locations.

Verification boundary

Before a backend consumes VIR, a verifier should check that referenced values, blocks and functions exist; control-flow edges and terminators are valid; definitions and uses follow the selected IR model; call signatures and operand types match; conversions are legal; and target-specific operations are supported. Serialized IR must be treated as untrusted input and verified again after loading.

Current status: VIR construction, verification, lowering and interpreter execution are implemented for the supported subset. The verifier rejects malformed structures and invalid branch targets. Consult the core roadmap and tests for exact acceptance scope.

9. Native compilation pipeline

Native machine-code generation remains planned work within VIB. The current working route lowers supported source constructs to VIR, verifies the representation and executes it with the VIR interpreter. Future native code generation must consume verified VIR without reparsing source or delegating Vayu semantics to an unrelated compiler.

A complete backend will need control-flow lowering, instruction selection, register allocation and spilling, calling conventions, stack frames, symbol tables, relocations, target-specific sections, object-format validation and reliable diagnostics. Unsupported constructs must fail explicitly before a misleading artifact is reported as successful.

10. Runtime, ABI and memory model

The runtime contract defines how generated code interacts with language values and operating-system services. Its design must be explicit before native code can safely call runtime helpers.

  • Values: define representation for integers, floating-point values, booleans, strings, collections, objects and references as each becomes supported.
  • Calls: specify argument passing, return values, stack alignment, preserved registers and error propagation for each target ABI.
  • Memory: document allocation, ownership/lifetime, reference safety, bounds checks and cleanup rules rather than relying on accidental host behavior.
  • Exceptions and failures: define how runtime errors, exceptions and process exit status cross execution boundaries.
  • Interop: foreign calls must have explicit type, ownership and ABI rules; a foundation or example is not proof of complete FFI coverage.

Current status: these remain requirements for a future native backend. The current VIR interpreter executes the implemented subset; a complete native runtime and ABI are not yet available.

11. Targets, object files and linking

The intended pipeline separates code generation from final linking. VIB owns VIR and machine-code generation; platform tools may provide system libraries, SDK components and final-link services behind a narrow adapter.

Target support should be advertised per operating system, architecture, ABI and tested language-feature subset. A command-line option or target enum alone does not establish a working target.

12. Artifact identity, caching and incremental builds

Future build acceleration must preserve correctness. A cache entry is reusable only when every relevant input matches.

  • Artifact identity should include source contents, imported dependencies, compiler revision, VIR schema, target/ABI, optimization settings, runtime ABI and relevant external tool identity.
  • Cache writes should be transactional: write to a temporary path, validate the artifact, then atomically commit metadata and output.
  • Failed builds must not leave cache entries that appear valid. Corrupt, incomplete or incompatible entries should be rejected and rebuilt.
  • Incremental compilation should track dependencies and invalidate all affected outputs. Its output must match a clean build.
  • Diagnostics should explain cache hits, misses and invalidation reasons without exposing unstable internal details as a promised interface.
Current status: opt-in content-addressed artifact caching is implemented for supported native-mode/package workflows. Dependency-aware incremental native compilation remains future work.

13. Diagnostics, observability and failure handling

A dependable compiler should fail early and explain the failure at the right abstraction level.

  • Validate CLI options and conflicting modes before starting compilation.
  • Distinguish syntax, semantic, IR-verification, unsupported-feature, target, emission, linker and runtime failures.
  • Include source location, selected mode, target and actionable context when available.
  • Propagate external tool exit status and bounded diagnostic output; do not confuse process launch with successful linking.
  • On failure, remove or mark incomplete outputs and never publish them as successful artifacts.
  • Keep deterministic diagnostic tests for malformed source, unsupported constructs, invalid options, corrupt IR, missing tools and failed linking.

14. Testing, correctness and performance

Correctness before speed

The interpreter and VM provide current routes for tests. As new routes are implemented, compare stdout, stderr, exit status, expected errors and observable side effects for the same fixture. Preserve minimized reproductions for any disagreement.

Test layers

  • Unit tests for lexer/parser, semantic checks, bytecode operations, IR invariants and target helpers.
  • Integration tests for driver flags, route selection, output paths, runtime behavior and linker failures.
  • Negative tests for malformed input, unsupported language features, invalid IR, corrupted artifacts and missing tools.
  • Regression and differential tests that compare every applicable execution route.
  • Clean-build versus incremental-build equivalence tests when incremental compilation exists.

Benchmark discipline

Measure startup, frontend time, compilation time, execution time, peak memory, artifact size and cache behavior separately. Use reproducible workloads, warm-up where applicable, multiple runs and disclosed hardware/tool versions. Predicted speedups are hypotheses, not measured results. Do not publish a native-performance claim before a working native backend and reproducible benchmark evidence exist.
